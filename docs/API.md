# The automation API

Gateshift carries a JSON API at `/api/v1` for programs: the nouns of a
migration (Devices, projects, interfaces, zones, rules, findings, jobs) as
JSON, authenticated with a token. The page's own routes are not an API and
stay out of this document.

The document of the API is generated by the application and is the
authority for the fields: `https://<server>/api/v1/openapi.json`, browsable
at `https://<server>/api/v1/docs`.

## Tokens

A signed-in user creates a token on the Automation page (`/automation`,
under Manage in the navigation): a name for the program it is for, a scope, an expiry when wanted,
a tenant when the installation has several. The token is shown once. A
program sends it on every call:

```
Authorization: Bearer gs_...
```

The scope says what the installation accepts from the token: `read` the
reads, `project` the writes of a project as well (curation, refresh, build,
review), `full` everything, which adds the push, the publish and the discard,
the Device life cycle (register, edit, delete, import, collect), projects
created and deleted, the keys of the tunnels. A call past the scope answers
403 with the scope it needs. A token for an agent gets `project`: it curates
and builds, it never pushes. A tenant-bound token sees and writes only its
tenant's Devices and projects, the others answer 404 like things that do not
exist, and a `tenant_id` in a query or a body is ignored. A live token's name
is taken once.

A session cookie never authenticates an API call, a token never opens a
page. The API's own document (`/api/v1/docs`, `/api/v1/openapi.json`) is the
one thing both open. A revoked or expired token never authenticates again.
Failed tokens count per address like failed logins and are slowed down the
same way. Before the installation has its account (the first visit of
`/setup`) every call answers 503 with the sentence "setup pending".

## Answers and errors

Every answer is JSON. An error of a call the API knows is a sentence:

```
{"error": "no project with id 42"}
{"error": "the request is not valid", "hint": "project_id: Input should be a valid integer"}
```

with 400 (bad input), 401 (no or bad token), 403 (the token's scope falls
short), 404 (no such noun), 409 (the state refuses, the sentence names why),
422 (validation), 429 (too many failed tokens from this address), 502 (the
Device did not answer), 503 (setup pending). A path the API does not know
answers 404 with `{"detail": "Not Found"}`, a method a known path does not
take 405 with `{"detail": "Method Not Allowed"}`. No redirects, no HTML. A
failure inside Gateshift answers 500 with `{"error": "the request failed
inside Gateshift", "ref": "<id>"}` and nothing of the exception. The
server log carries the text under that id.

Every write body takes an optional `reason`, one sentence of at most 200
characters, which lands in the audit beside what was changed (the calls
without a body take it as the query parameter `reason`). The Check Point
probe is a read, its body takes no `reason`.

## Version 1, the reads

| Call | Answers |
|---|---|
| `GET /api/v1/devices?tenant_id=` | the Devices of a tenant (the first tenant when absent) |
| `GET /api/v1/devices/{id}` | one Device with its manager scopes and its last import and collect jobs |
| `GET /api/v1/projects?tenant_id=` | the projects of a tenant with their pair and status |
| `GET /api/v1/projects/{id}` | one project with its progress (the step model) and the state of its last build, with the review stamp (`reviewed`, `current` when it names the current build) and the push stamps per strand |
| `GET /api/v1/projects/{id}/interfaces` | the project's interfaces as the Network tab shows them, with the project's names, zones, skips |
| `GET /api/v1/projects/{id}/zones` | the project's zones with their members |
| `GET /api/v1/projects/{id}/rules?limit=&offset=&hashes=` | the project's rules with its overrides, paged (`total`), each with its `rule_hash` (the content hash, the identity of a rule) and the fields of the rules table's row. `needs_refresh` says whether the ruleset pipeline has work pending (installation-wide). `hashes` (comma-separated, at most 200) answers only those rows, excluded rules among them stay out |
| `GET /api/v1/projects/{id}/findings` | the state, summary and report of the last build (findings, dropped fields, declared strands, completeness) and `kinds`, the step model's table of finding kinds with title, tab and the sentence that explains each |
| `GET /api/v1/jobs/{job_id}` | one job with its events, the push log's lines. Its `kind` is `import`, `collect`, `pipeline` (the ruleset refresh), `generate` (the build), `assign` (the application assignment) or `push` |
| `GET /api/v1/tenants` | the tenants of the installation with their counts (a tenant-bound token sees its own) |
| `GET /api/v1/whoami` | the calling token: `token_id` (the audit's), name, scope, tenant and expiry, never the token itself |
| `GET /api/v1/documents/{name}` | a shipped document as text: `operating` (OPERATING.md), `api` (this document), `known-limitations`, 404 when the installation does not carry it |

Credentials and pre-shared keys never come back through the API.

## Version 1, build and push as jobs

| Call | Does |
|---|---|
| `POST /api/v1/projects/{id}/build` | starts the build of the target configuration, 202 with `job_id`. A build already running answers 200 with its `job_id` and `already: true`. A body `{"target_cp_package": "..."}` names a Check Point package other than the Device's |
| `POST /api/v1/projects/{id}/reviewed` | body `{"job_id": "<the build>"}`: records that the findings of that build were reviewed, `reviewed` is false when it is not the current build any more |
| `POST /api/v1/projects/{id}/push` | body `{"strand": "network" or "policy", "build_id": "<the build reviewed>"?, "skip_sections": [...]?, "push_options": {"<key>": true}?, "mgmt_override": false?}`, scope `full`: starts the push, 202 with `job_id`. Without `build_id` the push does not check whether the configuration changed since the review, so a program names the build it reviewed. Every gate of the page applies: 409 when the strand is not pushed to this target, when nothing is built, when the configuration is outdated or changed since `build_id`, when a stored pre-shared key breaks the target's rule, 400 when the build still carries deleted items or a blocking finding |
| `POST /api/v1/jobs/{job_id}/publish` | scope `full`: publishes what the push job staged on a Check Point management, 202. The steps `publish` and `conflict check` land on the job's events |
| `POST /api/v1/jobs/{job_id}/discard` | scope `full`: drops what the push job staged, 202, the step `discard` on the job's events |

The push job's first event, `push parameters`, names the API client (the
token's name). A job is read with `GET /api/v1/jobs/{job_id}` until its
`status` is `done` or `failed`. Its `events` carry the push log's lines.
The three bodies refuse a field they do not know (422 with the field's
name), so a misspelt `build_id` stops the push instead of dropping the check.

A migration through the API, today: build, read the findings, mark the
build reviewed, then, with a token of scope `full`, push the network strand,
then the policy strand, publish each on a Check Point management, read the
job's events.

## Version 1, the writes of a project

Every write names its project or Device in the path and lands as one row of
the audit (`GET /api/v1/audit`, and the Automation page lists the latest):
the token's name, the call, what it touched. What a program sets reads like
a value set on the page, the audit says whose hand it was. Registering,
editing, deleting, importing and collecting a Device (and the Check Point
probe), creating and deleting a project and storing a tunnel's key need
scope `full`, the other writes `project`. The fields of the bodies are in
the document (`/api/v1/docs`). A body with a field the call does not know answers 422
with the field's name.

| Call | Does |
|---|---|
| `POST /api/v1/devices/checkpoint/probe` | body `{"mgmt_ip", "mgmt_port", "api_key", "domain"?, "package"?}`: reads a Check Point management as the add wizard does, the policy packages with how many gateways run each, the gateways and clusters with their installed package and whether Gateshift supports them, the Devices already registered against the management. The key travels in the body and is not stored. 502 when the management does not answer |
| `POST /api/v1/devices` | registers a Device like the add dialog: `platform`, `mgmt_ip`, `mgmt_port`, `api_key`, `gaia_user`, `gaia_password`, `notes`, `role`, `tenant_id`, and `options` for the dialog's further fields by their form names (ftd_username, opn_api_key_id, the FortiGate Cloud fields fgc_*). 201 with the Device, 400 with the dialog's sentence. With `checkpoint: {"gateway_uid", "gateway_type", "policy_package", "domain"?}` the wizard's last step runs: the gateway is re-read from the management, the Gaia credentials are probed when given, 409 with `existing_device_id` when that gateway and package are registered already |
| `PATCH /api/v1/devices/{id}` | edits like the edit dialog. A field left out keeps its value. The platform is immutable, `api_key` and `gaia_password` are write-only (a Check Point gateway's new Gaia password is probed first, as on the page), `tenant_id` moves a Device no project binds (a tenant-bound token moves none), `options` carries nat_mode, routing_mode, ftd_username, opn_api_key_id |
| `DELETE /api/v1/devices/{id}` | deletes the Device and what was imported from it, 409 with the projects' names while projects use it |
| `POST /api/v1/devices/{id}/import` | imports the Device's configuration, 202 with `job_id`. An import already running on the Device is returned instead (`already`). The job's events are the Device log's lines, the first names the API client |
| `POST /api/v1/devices/{id}/collect` | collects interfaces and routes, 202 with `job_id` |
| `POST /api/v1/projects` | body `{"source_id", "target_id", "name"?}`: a new project of the pair, 201 with the project, 409 when the name exists in the tenant or the pair spans two tenants |
| `PATCH /api/v1/projects/{id}` | body `{"name"?, "status"?}`: renames the project, sets `draft`, `verified` or `closed` (the step model keeps the last word, as on the page) |
| `DELETE /api/v1/projects/{id}` | removes the project and every decision it holds, the Devices stay |
| `PATCH /api/v1/projects/{id}/interfaces/{iface_id}` | one interface of the project's network scope, with the fields `GET .../interfaces` lists: `name` (the target's name, the project's rename, sub-interfaces follow), `zone` (bind, by shown name, a new name creates the project's zone, null unbinds), `skip`, `type`, `enabled`, `description`, `role`, `vr`, `parent`, `vlan_tag`, `ip_addresses`, `dhcp`, `members`, and beside them `zone_color` (the colour of the zone named in `zone`, blue for a new zone when absent). 404 for an interface of another Device, 409 with `confirmable` when a skip would empty a zone rules still use (repeat with `confirm_empty_zone: true`), 409 when a name is taken |
| `POST /api/v1/projects/{id}/refresh` | runs the ruleset pipeline, 202 with `job_id`: an import leaves the rules behind the facts (`GET .../rules` says `needs_refresh`), the build runs the pipeline as its first stage anyway, a program that curates rules before the build refreshes here |
| `POST /api/v1/projects/{id}/rules/disable` | body `{"rule_hashes": [...], "disabled": true}`: disables the rules in this project (the rules stay in the Device's facts). `disabled: false` enables them again. Answers how many rules changed state |
| `POST /api/v1/projects/{id}/rules/exclude` | body `{"rule_hashes": [...]}`: leaves the rules out of this project, the project's delete |
| `POST /api/v1/projects/{id}/rules/restore` | body `{"rule_hashes": [...]}`: brings excluded rules back, `not_excluded` names the hashes that were not excluded |
| `GET /api/v1/projects/{id}/exclusions` | what the project leaves out, by kind (rules, routes, interfaces, ...) |
| `POST /api/v1/projects/{id}/exclusions/restore` | body `{"device_id", "kind", "item_key"}`: brings one excluded item of any kind back |
| `POST /api/v1/projects/{id}/target-inventory` | fetches the target's inventory (interfaces, zones, VRs, routes and the platform's catalogues) from the Device into the snapshot the Network tab reads, one kind after the other as the page does, and writes nothing to the Device. It answers `fetched`, `not_on_this_platform`, `failed`, `warnings`, 502 when nothing could be read |
| `POST /api/v1/projects/{id}/zones` | body `{"name", "color"?}`: creates the project's own zone, 409 when the name exists or another zone is shown under it |
| `DELETE /api/v1/projects/{id}/rule-zones` | removes every rule zone override of the project, derived and manual |
| `POST /api/v1/projects/{id}/rule-zones/auto` | derives every rule's zones from the routes and the interfaces' bindings as derived overrides. Manual picks stay. It answers `mapped`, `skipped_manual`, `no_match` |
| `GET /api/v1/projects/{id}/vrfs` | the project's virtual routers |
| `DELETE /api/v1/projects/{id}/vrfs/{name}` | deletes a virtual router in this project: an imported one becomes an exclusion, the project's own is removed, its interfaces and routes re-home to default, 409 for `default` |
| `GET /api/v1/projects/{id}/settings` | the target's push settings with the project's values, by key, as the Profiles & Settings tab shows them (a Check Point package pin reads as `pinned`) |
| `PUT /api/v1/projects/{id}/settings` | body `{"settings": {"<key>": "<value>"}}`: sets push settings of the target for this project. The target configuration is outdated afterwards |
| `GET /api/v1/projects/{id}/vpn` | the source's VPN tunnels with their `vpn_hash` and `psk_set`, never a key |
| `PUT /api/v1/projects/{id}/vpn/{vpn_hash}/psk` | body `{"psk": "..."}`: stores the tunnel's pre-shared key for the push, checked against the target's rule (400 with the sentence). An empty key clears the stored one. The key is never read back |
| `GET /api/v1/audit?project_id=&device_id=&limit=&offset=` | the writes made through the API, newest first, each with the token's name |

A rule write, a settings write and an exclusion restore mark the project
curated, as the page's writers do. The API never creates a project on the
way: a project in a path that does not exist answers 404.

A migration through the API, end to end: probe the management and register
the Devices, import both as jobs, create the project, rename and skip the
interfaces and bind the zones, refresh the ruleset, disable or exclude what
is not to be migrated,
set the push settings and the keys of the tunnels, build, read the findings,
mark the build reviewed, push the network strand, then the policy strand,
publish each on a Check Point management, read the audit.

## Version 1, the curation of objects, names and rule fields

The writes an operator does on the Objects tab and in the enrichment panes.
Every one is project-own: a rename is a row of
the project's name map, a delete an exclusion, a field a per-rule override.
Every write takes `reason` and lands in the audit.

| Call | Does |
|---|---|
| `GET /api/v1/projects/{id}/objects?kind=&q=&limit=&offset=&flags=1` | the project's objects of one kind (`address`, `service`, `address_group`, `service_group`, `schedule`) as the Objects tab shows them, `name` beside `source_name`, `q` filters by name, value or description, `flags=1` adds the lint flags per row (`unused`, `dup_name`, `dup_value`, `dup_member`, `member_value_dup`) |
| `PATCH /api/v1/projects/{id}/objects/{kind}/{obj_id}` | body `{"name"}`: shows the object under another name in this project (the name map), 409 with the sentence when another entity carries or is shown under it |
| `DELETE /api/v1/projects/{id}/objects/{kind}/{obj_id}` | leaves one object out of the project, 409 `blocked` with the reasons when a rule, group or NAT of the project still needs it |
| `POST /api/v1/projects/{id}/objects/delete` | body `{"items": [{"kind", "id"}], "dry_run"}`: the partition `deletable`, `blocked` (with the reasons), `not_found`. `dry_run: false` excludes the deletable ones |
| `POST /api/v1/projects/{id}/objects/merge` | body `{"kind": "address"\|"service", "buckets": [{"canonical": {"id"}, "losers": [{"id"}]}], "dry_run"}`: the losers map to the canonical's name and leave the project, `refs_rewritten` counts the references that follow |
| `GET /api/v1/projects/{id}/names?kind=` | the project's name map: `kind`, `source_name`, `target_name`, `orphan` (the source no longer carries the name) |
| `POST /api/v1/projects/{id}/rename` | the naming workbench: `{"kind": object\|service\|interface\|zone\|vrf\|nat_rule\|rule, "select": {"names": [...]} \| {"hashes": [...]} \| {"all": true, "contains"?}, "pattern", "replace": [{"from", "to"}]?, "case": keep\|lower\|upper, "mapping": {key: name}?, "dry_run"}`. Either `pattern` with `select` or `mapping` (source name or rule hash to the new name). The pattern's variables: `{name}` (the shown name), `{source}`, `{n}` and `{n:03}` (the ordinal), `{device}`, `{kind}`, for rules `{action}`, `{src_zone}`, `{dst_zone}`. `replace` and `case` act on `{name}`. The answer is the plan: `changes` (with `over_limit` where the target's renderer would truncate), `refused` with a sentence each, `unchanged_total`, `inverse` (the map that undoes the batch). The plan is a set: a collision refuses the whole batch with 409, nothing is written. `dry_run: false` writes. Caps: 500 items, 200 rules |
| `POST /api/v1/projects/{id}/rules/zones` | body `{"rule_hashes", "src_zone"?, "dst_zone"?}`: a name adds it to the side, `any` resets the side, `__auto__` derives it from the routes, null keeps. `POST .../rules/zones/clear` `{"rule_hashes"}` removes the overrides |
| `PUT /api/v1/projects/{id}/rules/service` | body `{"rule_hashes", "service"}`: `any`, `application-default` (refused for a Check Point target, whose renderer reads `any` alone) or null to clear |
| `PUT /api/v1/projects/{id}/rules/applications` | body `{"rule_hashes", "applications"}`: `["any"]`, names from the target's stored catalogue (400 names an unknown one), `[]` clears to empty, null removes the override |
| `PUT /api/v1/projects/{id}/rules/profiles` | body `{"rule_hashes", "profile_group"?, "slots"?}`: PAN-OS a group or the `pa_*` and `av_profile`, `webfilter_profile` slots, FortiGate the UTM slots, neither clears the row. Refused for a Check Point target |
| `PUT /api/v1/projects/{id}/rules/logging` | body `{"rule_hashes", "profile"?, "log_start"?, "log_end"?, "log_traffic"?, "capture_packet"?}`: PAN-OS reads profile, log_start, log_end, FortiGate log_traffic (`all`, `utm`, `disable`), log_start, capture_packet, a field the target's renderer does not read answers 400, an empty body clears |
| `PUT /api/v1/projects/{id}/rules/track` | body `{"rule_hashes", "track_type"?, "accounting"?, "per_session"?, "per_connection"?}` on a Check Point target, no track_type clears |
| `PUT /api/v1/projects/{id}/rules/schedule` | body `{"rule_hashes", "schedule"}`: a schedule's name, `none` for no schedule, null clears the override |
| `PUT /api/v1/projects/{id}/rules/negate` | body `{"rule_hashes", "aspect": source\|destination\|service, "value"}` |
| `PUT /api/v1/projects/{id}/rules/names` | body `{"names": {"<rule_hash>": "<name>"}}`: the rules' names in this project, an empty name clears, a duplicate is refused like the workbench does |
| `POST /api/v1/projects/{id}/rules/move` | body `{"rule_hash", "before"\|"after": "<rule_hash>"}`: places the rule, the build renders that order, 409 for rules without a source order (a log source) and for two rules of different Devices |
| `DELETE /api/v1/projects/{id}/rules/order?rule_hashes=&reason=` | removes the order overrides named, all without the parameter |
| `GET /api/v1/projects/{id}/catalog/{kind}` | the target's stored catalogue (`applications`, `security_profiles`, `log_forwarding`, `utm_profiles`, `threat_layers`, `threat_profiles`) with `read_at`, 404 when nothing is stored. `zones` is the picker's catalogue of the source's zones and interfaces |
| `POST /api/v1/projects/{id}/catalog/{kind}/refresh` | reads the catalogue from the target Device and stores it (a project write: the installation opens a session to the Device) |
| `POST /api/v1/projects/{id}/applications/assign` | body `{"mode": ports\|names, "rule_hashes"?}`: the automatic application assignment as a job, 202 with `job_id` (an assign already running on the project is returned, `already`). The job's last event carries the counters in `data` (`matched`, `partial`, `skipped_manual`, `unmatched_names`). Manual picks are kept |

The rules read (`GET .../rules`) shows the project's names on the rules'
tokens and carries `source_rule_name` and `source_sequence` beside the
effective name and position. A job's events carry `data` where the job wrote
some.

## Version 1, the network strand, the NAT rules and the snapshots

The additions, edits and deletes of the Network tab and the NAT tab, and the
snapshots of a project's decisions. The
reads carry `own` on every row: the project's own addition against a fact of
the Device. A row is addressed by its id (interfaces, routes, zones, virtual
routers) or by its hash (NAT rules, whose ids change at every import). A row
of another Device, or another project's addition on the same Device, answers
404. Every write takes `reason` and lands in the audit. The fields of a kind,
with their types, enums and a sentence each, come from `GET
.../kinds/{kind}`, together with the target's property keys for zones and
NAT rules. A body with a field the route does not know answers 422, a
property key the target's schema does not know 400 with the keys.

| Call | Does |
|---|---|
| `GET /api/v1/projects/{id}/routes` | the routes of the project's network scope: prefix (CIDR), interface, next hop, virtual router, metric, route type, the interface's zone, `edited` and `own` |
| `GET /api/v1/projects/{id}/nat-rules` | the NAT rules of the project's source as the NAT tab shows them: `nat_hash`, name, type, zones, the original and translated sides, disabled, description, properties, the negates, the override markers (`*_override_source`) and `own`, names in project space |
| `GET /api/v1/projects/{id}/snapshots` | the snapshots, newest first: id, name, kind (`original`, `manual`, `auto`), note, `created_at`, `rows`, and `source_changed` when the source or target was imported again since |
| `GET /api/v1/projects/{id}/kinds/{kind}` | the fields of `interface`, `route`, `vrf`, `zone` or `nat_rule` for add, edit and delete, how a row is addressed, and the target platform's property keys |
| `POST /api/v1/projects/{id}/interfaces` | body `{"name", "type"?, "parent"?, "vlan_tag"?, "ip_addresses"?, "zone"?, "description"?, "dhcp"?}`: the project's own interface, its zone created when the project has none of that name, one connected route per address, 201 with the id, 409 with `reason` (`excluded`, `own`, `other_project`, `source`, `shown`, `overlap`) |
| `DELETE /api/v1/projects/{id}/interfaces/{iface_id}?confirm_empty_zone=1&reason=` | an imported interface becomes an exclusion with its routes, the project's own row is removed, 409 with `confirmable` when it is the sole member of a zone rules still use |
| `POST /api/v1/projects/{id}/routes` | body `{"prefix", "interface"?, "next_hop"?, "vr"?, "metric"?, "route_type"?}`: the project's own route, 409 with `reason` when the prefix exists in that virtual router |
| `PATCH /api/v1/projects/{id}/routes/{route_id}` | body `{"prefix"?, "next_hop"?, "interface"?, "metric"?, "route_type"?}`: an imported route gets the project's edit row, a new prefix is an exclusion plus an addition, the project's own row changes in place |
| `DELETE /api/v1/projects/{id}/routes/{route_id}?reason=` | an exclusion keyed prefix\|vr, or the own row removed |
| `POST /api/v1/projects/{id}/vrfs` | body `{"name"}`: the project's own virtual router, 409 with `reason` on a duplicate |
| `PATCH /api/v1/projects/{id}/zones/{zone_id}` | body `{"color"?, "is_external"?, "properties"?}`: an imported zone's values are the project's edit, an own zone changes in place. The name goes through `/rename` |
| `POST /api/v1/projects/{id}/zones/properties` | body `{"zone_ids" (at most 50), "properties"}`: the properties merged per key over each zone, `not_in_project` names the ids dropped |
| `DELETE /api/v1/projects/{id}/zones/{zone_id}?cascade=1&reason=` | 409 with `referrers`, `cascade_available` and `member_interfaces` while rules or interfaces use the zone. `cascade=1` takes an auto-snapshot, moves the project's rules from the zone to its members' shown names (zone overrides) and deletes. NAT and Policy Routing referrers still refuse |
| `POST /api/v1/projects/{id}/nat-rules` | body `{"name", "nat_type", "src_zones"?, "dst_zones"?, "interface"?, "orig_src"?, "orig_dst"?, "orig_service"?, "trans_src"?, "trans_src_type"?, "trans_dst"?, "trans_dst_port"?, "description"?, "disabled"?}`: the project's own NAT rule with its hash. Names arrive in project space and are stored as source names slot for slot. It answers 409 with `reason` when another rule carries or is shown under the name |
| `PATCH /api/v1/projects/{id}/nat-rules/{nat_hash}` | body `{"name"?, "description"?, "disabled"?, "properties"?, "src_zone"?, "dst_zone"?, "negate_source"?, "negate_destination"?, "negate_service"?}` in one transaction. An imported rule's values go into the project's override row, the name into the name map. A hash input (type, zones, sides) is refused: delete and add instead. It answers 409 `ambiguous` with the names when two imported rules share the hash |
| `POST /api/v1/projects/{id}/nat-rules/bulk` | body `{"nat_hashes" (at most 50), "disabled"?, "description"?, "properties"?, "src_zone"?, "dst_zone"?}`, an empty zone string clears the overlay, `not_in_project` names the hashes dropped |
| `PUT /api/v1/projects/{id}/nat-rules/negate` | body `{"nat_hashes" (at most 50), "aspect": source\|destination\|service, "value"}` |
| `DELETE /api/v1/projects/{id}/nat-rules/{nat_hash}?reason=` | an imported rule becomes an exclusion keyed on its hash, the own row is removed with its override rows |
| `POST /api/v1/projects/{id}/snapshots` | body `{"name", "note"?}`: a snapshot of the project's decisions, 201 with the id and the row count |
| `POST /api/v1/projects/{id}/snapshots/{sid}/restore?reason=` | the project's decisions as the snapshot holds them, after an auto-snapshot of the state before. The report carries `restored`, `removed`, `orphans`, `auto_snapshot`, `source_changed`. It answers 409 while a build of the project runs. The artefact is marked outdated |
| `DELETE /api/v1/projects/{id}/snapshots/{sid}?reason=` | 409 for the Original and for an auto-snapshot (the undo of a restore or a cascade) |
| `POST /api/v1/projects/{id}/snapshots/{sid}/branch` | body `{"name"}`, scope `full`: a new project of the pair from the snapshot's decisions, 201 with its id. A row the snapshot added (an interface, route, zone, virtual router or NAT rule) whose key another project of the Device still holds, the parent above all, stays out and is counted as `held` in the report, as on a restore |

What survives a collect and an import: additions of every kind (interfaces,
routes, zones, virtual routers, NAT rules) stay the project's. A zone or
virtual router addition whose name the source now claims becomes a shared
fact, a route or interface addition under a claimed name is removed. The
edit rows of imported interfaces, routes and zones ride the name or prefix
and orphan when the row leaves. NAT edits and exclusions ride the hash. The
ids of interfaces, zones, virtual routers and routes are the current
import's, and a restore renumbers the additions, so a client resolves ids
per session (the MCP tools do per call). No addition reaches a Device
before a push, and a push needs the operator on the Review & Deploy page or
a token of scope `full`.

## What comes next

Version 1 grows in place: the registrations by upload (a configuration file,
a cloud bundle, a log file) and the enrichment of Policy Routing,
decryption and VPN follow in the same shape. A breaking change would open
`/api/v2` beside this one.
